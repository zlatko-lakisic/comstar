# COMSTAR Phase 2 — Proactivity and the text channel

**Audience:** an AI coding agent (Cursor / Claude Code) plus one human operator.
**Companions:** `AGENTS.md` · `docs/CONTRACTS.md` · `docs/IMPLEMENTATION_PLAN.md` · `docs/TESTING.md`
**Gate:** M9 exit criteria are all checked. Do not start M10 before then.

---

## Why these two, and why in this order

Everything COMSTAR does today starts with a human. Every transition in CONTRACTS §8 originates from a sensor or a person. There is no path where the device says something you did not ask for.

That is the gap worth closing, and closing it is worth more here than it is anywhere else, because COMSTAR knows who is standing in the room. A messaging bot that pings you at 9am is a commodity. A terminal that waits until you actually walk past it and then says the one thing you needed to hear is not. Presence is the asset; proactivity is what makes the asset pay.

The channel comes second, and deliberately smaller than it sounds. The point is not channel breadth. It is that a conversation started in the kitchen should still exist when you are on a train. One channel, one identity, shared memory.

| # | Name | Effort | Ships |
|---|---|---|---|
| M10 | Proactive announcements | 26h | COMSTAR speaks first, to the right person, at the right moment |
| M11 | Text channel | 24h | One messaging surface sharing identity and memory with the terminal |

**M10 introduces no new attack surface. M11 introduces internet-facing ingress into a system that can control your house.** That ordering is not negotiable.

# M10 — Proactive announcements

**Goal:** an external event produces an utterance that COMSTAR delivers to a specific person, at a moment it chose, without being asked.

**Why here:** it reuses the state machine, the session, the TTS path and the greeter. Nothing new crosses a trust boundary. It is the highest ratio of product change to architectural change available to you.

---

## M10.0 — Ground truth *(3h)*

**M10.0.1 — The session ownership question** *(1.5h)*
An announcement needs an AO turn to generate its text, and that turn happens when there may be no session open. Determine empirically: can the announcer generate text through a short-lived `SessionBridge` under `x-agentic-user-name: <userid>` while a terminal session for the same identity is open or closed, without disturbing the terminal's session or leaking overlays? Write the answer into CONTRACTS §4.

If two concurrent bridges for one identity are not safe, the fallback design is that the announcer never opens its own bridge and instead enqueues *intent*, with text generated by the terminal's session at delivery time. That is a materially different build. **Answer this before writing M10.2.**

**M10.0.2 — Quiet-hours and wake-state reality check** *(1h)*
The Pi screen and speakers may be off or dimmed. Confirm what `screen_state` actually reports overnight and whether audio output is available. An announcement into a muted speaker is a silently dropped announcement.

**M10.0.3 — Write `docs/adr/0009-proactivity.md`** *(0.5h)*
Record the session-ownership decision and the delivery policy from M10.3.

### Exit criteria
- [x] Session ownership question answered in writing, CONTRACTS §4 updated (2026-08-07)
- [x] Overnight screen and audio state recorded in `docs/BASELINES.md` §13
- [x] ADR written (`docs/adr/0009-proactivity.md`)

## M10.1 — Announcement types and the queue *(3h)*

`lib/announce/types.dart`, `lib/announce/queue.dart`.

```dart
class Announcement {
  final String id;              // ULID
  final String recipient;       // userid, or 'any'
  final String source;          // 'schedule' | 'event' | 'agent'
  final String intent;          // what to say, or the prompt that generates it
  final Priority priority;      // normal | urgent
  final DateTime notBefore;
  final DateTime expiresAt;     // hard TTL
  final String? dedupeKey;
}
```

Persisted to SQLite so a bridge restart does not lose the queue. Two priorities only. Resist a third.

**TTL is load-bearing.** A reminder about a 2pm meeting delivered at 4pm is worse than no reminder, because it teaches the user to stop listening. Expiry is silent and logged, never delivered late.

**Dedupe on `dedupeKey`.** A schedule that fires every 15 minutes must not produce four queued copies of the same thing.

### Exit criteria (M10.1)
- [x] `lib/announce/types.dart` + `lib/announce/queue.dart` (SQLite, TTL, dedupe)
- [x] `test/announce_queue_test.dart` — notBefore, TTL, dedupe, restart, priority order

## M10.2 — Sources *(5h)*

Three, built in this order. Each is a process that only ever enqueues; none of them can deliver.

**M10.2.1 — Scheduled** *(2h)*
`announce/schedule.yaml`, cron-style. Fully offline-testable, which is why it goes first. Entries name a recipient, a time expression, a prompt, and a TTL.

**M10.2.2 — Event-driven** *(2h)*
Subscribes to MQTT / Home Assistant, the source already in your Phase 2 list. An HA event maps to an announcement through a declarative rule file, not code.

**M10.2.3 — Agent-initiated** *(1h)*
A hosted MCP tool `enqueue_announcement` so the orchestrator can schedule its own follow-up. "Remind me when I get home" becomes a tool call rather than a feature.

**Hard rule: sources enqueue, the machine delivers.** No source may call `Speak` directly. This is the same separation as CONTRACTS §8 invariant 6, and it is what keeps delivery policy in one testable place.

---

## M10.3 — Delivery gate *(5h)*

`lib/announce/gate.dart`. The heart of M10. Runs on every `Tick` and on entry to `engaged`.

| Attention state | `normal` | `urgent` |
|---|---|---|
| `ambient` | hold | hold |
| `noticed` (identity unresolved) | **hold** | **hold** |
| `engaged`, identity == recipient | deliver | deliver |
| `engaged`, identity != recipient | hold | hold |
| `listening` | hold | hold |
| `responding` | hold | hold |
| quiet hours | hold | deliver |

Two rows deserve emphasis.

**`noticed` always holds, both priorities.** Identity is unresolved there. Delivering means announcing someone's calendar to whoever happened to walk in. This is a security boundary of exactly the same kind as the guest-session restriction in M5.3, and it gets a test that says so.

**`listening` and `responding` always hold.** Never interrupt a turn in progress. Barge-in from the device is a different and much worse experience than barge-in from the human.

Coalescing: when multiple announcements clear the gate for the same person at the same moment, they become **one** utterance, not a queue drained back to back. Cap at three items; anything beyond that becomes "and a few other things."

---

## M10.4 — Machine integration *(4h)*

Two additions to CONTRACTS §8 and nothing more.

New event: `AnnouncementReady(id, text, audio)`.

| from | event | guard | to | side effects |
|---|---|---|---|---|
| engaged | AnnouncementReady | gate passed | responding | `speak` to kiosk, mark delivered |

Delivery reuses `responding` rather than adding a state. It behaves identically from there: `PlaybackEnded` returns to `engaged` and opens the follow-up window, which is exactly what you want. COMSTAR tells you your 2pm moved, and you can answer it without a wake word.

Two new invariants:

> **7.** An announcement is delivered only when state is `engaged` and the cached identity equals the announcement's recipient, or the recipient is `any`.
>
> **8.** At most one announcement utterance per entry into `engaged`.

---

## M10.5 — Fold into the greeting *(2h)*

When an announcement clears the gate on the same Engaged transition that triggers the greeting, they become one utterance from the `greeter` agent, not two. "Morning Zlatko, your 2pm moved to 3." Two consecutive utterances is the tell that a feature was bolted on.

M8.2's 1.5s greeting budget still applies. If announcement text is not pre-generated by then, the greeting ships alone and the announcement waits for the next gate evaluation.

## M10.6 — Dev console and observability *(4h)*

Add to DEV_LOOP §2:
- Queue inspector: pending, held-and-why, delivered, expired
- **Inject announcement** button, matching the existing injection pattern, tagged `src: "injected"`
- Force gate evaluation
- Skip-to-time control for testing TTL and quiet hours under the fake clock

Every hold logs the *reason*. "Why didn't it tell me?" must be answerable from `make logs` without a debugger.

### Automated tests
- `queue_test.dart` — TTL expiry is silent and logged; dedupe collapses repeats; survives a restart; `notBefore` respected under fake clock.
- `gate_test.dart` — every cell of the M10.3 table has a named test. **The `noticed` rows and the identity-mismatch rows are asserted as security boundaries, in the same file as the M5.3 guest tests.**
- `coalesce_test.dart` — three clearing announcements produce one utterance; four produce three plus a summary; ordering is by priority then age.
- `announce_machine_test.dart` — invariants 7 and 8 hold across the existing 10,000-sequence property test, extended with announcement events.
- Golden scenarios: announcement queued while nobody home and delivered on arrival; queued for A and delivered while B is present (must not fire); expires unheard; arrives mid-turn and waits.

### UAT
`UAT-10`. Schedule something for five minutes out, leave the room, come back. Then repeat with someone else standing there instead of you.

### Exit criteria
- [x] An announcement queued with the room empty is delivered within 5 s of you being recognised *(path wired; UAT-10 operator)*
- [x] The same announcement is **never** delivered to a different recognised person, or in `noticed` *(gate tests)*
- [x] Greeting and announcement arrive as one utterance *(greeter fold)*
- [x] Expired announcements are dropped silently and the reason is in the log *(queue tests)*
- [x] A source cannot cause speech except through the queue, asserted by test *(sources enqueue only)*
- [ ] 24h soak: zero unprompted utterances that were not queued announcements *(wall-clock)*

### Risks
- **This is the feature that makes the device annoying.** Every delivery policy failure is felt as the machine talking out of turn, which erodes trust much faster than a slow answer does. Tune conservatively: when in doubt, hold.
- **Announcement text quality.** The voice_responder's 40-word spoken constraint applies, but announcements are generated without a question to anchor them. Expect the first drafts to be verbose. This is a prompt problem in a new `announcer.yaml` overlay, not a plumbing problem.

# M11 — Text channel

**Goal:** messaging continuity away from the hallway — same household brain,
allowlisted / QR-paired senders only.

**Plane (ADR 0015):** native `ChannelMux` on Ada (`comstar-channel`). Telegram
ships first with **kiosk QR pairing** (same `pairing.qr` UX as Google).
WhatsApp and Signal join as additional `Channel` implementations when backends
are configured. **Do not route messaging through OpenClaw.**

Original Telegram-first scaffold notes below remain the M11.0–M11.5 base;
pairing + multi-provider extension is ADR 0015.

---

## M11.0 — Ground truth *(2h)*

**M11.0.1 — Shared session semantics** *(1.5h)*
Can two surfaces attach to `x-agentic-session-id: comstar-zlatko` concurrently, and does session memory merge as expected? If not, the design becomes separate session ids sharing KB scope by userid, and continuity becomes a KB property rather than a session property. Write the answer into CONTRACTS §4.

**M11.0.2 — ADR** *(0.5h)*
`docs/adr/0010-text-channel.md`, recording the channel choice and the session decision.

---

## M11.1 — Where it runs *(1h)*

**On the AI server, not the Pi.** The channel must work when the Pi is off, when you are not home, and when the room is empty. It is co-located with AO for the same reason `vision_mcp` is.

New systemd unit `comstar-channel` alongside the daemon.

---

## M11.2 — Channel abstraction *(3h)*

`channel/lib/channel.dart`. One interface: `inbound` stream of `(senderId, text, attachments)`, `send(senderId, text)`, plus typing indicators. `TelegramChannel` implements it. The interface exists so channel two is a day rather than a rewrite, and for no other reason.

---

## M11.3 — Identity and the allowlist *(3h)*

`channel/lib/identity.dart`. A static map from channel sender id to COMSTAR userid, in config, not a database.

**Anything not on the allowlist gets no response at all.** Not an error, not a greeting, not "you are not authorised." Silence. An unknown sender should be unable to distinguish COMSTAR from a dead bot.

This is the single most important paragraph in M11. The channel is an internet-facing ingress into a system that holds a Home Assistant MCP. There is no guest mode here and no stranger mode. The allowlist is the entire security model, so it is short, static, reviewable, and tested.

---

## M11.4 — Text responder overlay *(3h)*

`overlays/comstar/agent_providers/text_responder.yaml`.

**Do not reuse `voice_responder`.** Its prompt forbids markdown, lists and URLs and targets 40 words, all of which are correct for a TTS engine speaking to someone in a room and wrong for a chat window. Text gets markdown, gets links, and gets to be longer.

Same MCP set, different output contract. `overlays_test.dart` extends to assert both constraints exist and that neither file has drifted into the other's.

---

## M11.5 — Session wiring *(4h)*

`channel/lib/session.dart`, per the M11.0.1 finding. Sessions here are longer-lived than the terminal's and are not bounded by presence, so TTL and cleanup are their own concern. `stop()` on SIGTERM, same overlay-leak discipline as M5.1.

---

## M11.6 — Announcements over the channel *(3h)*

M10's queue gains a second delivery surface. New gate rows:

| Condition | Behaviour |
|---|---|
| Recipient present at the terminal | Terminal wins. Channel does not also fire. |
| Recipient absent, `urgent` | Deliver to channel |
| Recipient absent, `normal` | Hold for terminal until TTL, then drop |
| Delivered on either surface | Marked delivered globally |

The dedupe across surfaces matters more than it looks. Being told the same thing twice by two different mouths is the bug users remember.

---

## M11.7 — Rate limiting and cost *(2h)*

Per-sender rate limit and a daily orchestration-call cap. A messaging channel is a loop that a misbehaving client, or you at 2am, can drive indefinitely. The terminal is naturally rate-limited by a human standing in a room; the channel is not.

---

## M11.8 — Docs *(3h)*
CONTRACTS gains §11 (channel protocol, identity mapping, allowlist). README gains the channel to the architecture diagram and, importantly, to the **privacy model** section, which currently claims nothing leaves the LAN. That claim stops being true the moment M11 ships. Change the code or change the README, per M9.7.

### Automated tests
- `allowlist_test.dart` — unknown sender produces zero outbound bytes; a removed sender stops working immediately; sender ids are compared exactly, no normalisation surprises.
- `channel_session_test.dart` — same userid from terminal and channel reaches the same memory; overlay cleanup on SIGTERM; no leak over 20 cycles.
- `overlays_test.dart` (extended) — voice and text constraints both present and distinct.
- `announce_surface_test.dart` — presence at the terminal suppresses channel delivery; delivered-once across surfaces under concurrent gate evaluation.
- `ratelimit_test.dart` — per-sender cap under fake clock; daily cap; both reset correctly.

### UAT
`UAT-11`. Ask something in the kitchen, leave, continue it from Telegram. Then have someone not on the allowlist message the bot and confirm total silence.

### Exit criteria
- [ ] A conversation started at the terminal continues on the channel with context intact *(UAT-11)*
- [ ] Non-allowlisted senders receive nothing, ever, verified by packet-level check *(UAT-11)*
- [x] Text answers use markdown; spoken answers still do not *(overlays + tests)*
- [x] An urgent announcement reaches exactly one surface, never both *(CAS + gate tests)*
- [x] Rate limits hold under a scripted flood *(ratelimit tests)*
- [x] README privacy model updated and true

### Risks
- **This is the project's first internet-facing ingress.** Everything before this was LAN-only by construction. Treat M11.3 as the security review, and do it as a review, not as a task you tick.
- **Scope creep to channel two.** The abstraction makes it look free. It is not: every channel is another allowlist, another auth story, another set of formatting quirks. Ship one, live with it for a month.
